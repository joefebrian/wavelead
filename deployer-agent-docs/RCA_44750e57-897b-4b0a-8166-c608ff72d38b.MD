# RCA — WaveLead redeploy failed at build_image (run 44750e57-897b-4b0a-8166-c608ff72d38b)

## Summary
The redeploy failed in the `build_image` step during the frontend dependency install. It is a **source-level inconsistency between `package.json` and `yarn.lock`** — not a platform, manifest, secret, DB, or infra problem. The build never produced an image, so **production is untouched and still serving the previous build** (run `df981f72-8a5c-4a69-99ef-4c5faaa4b73c`, image `sha256:790216bc…`).

## Evidence (Cloud/CodeBuild log, step #12 `[builder 5/9]`, all 3 retries identical)
```
warning Resolution field "postcss@8.5.10" is incompatible with requested version "postcss@8.4.31"
error Your lockfile needs to be updated, but yarn was run with `--frozen-lockfile`.
```
The build runs `yarn --frozen-lockfile --network-timeout 100000`. yarn aborts because, to satisfy the `resolutions` override in `package.json` (`postcss` pinned to **8.5.10**), it would have to rewrite `yarn.lock`, which currently records **postcss@8.4.31**. `--frozen-lockfile` forbids any lockfile mutation, so it exits 1. Retried 3×, same result → terminal build failure.

## Why this happened
Per the release note, `yarn.lock` was "put back to the committed version (same lockfile as the current production build)." That revert is exactly what broke the build: the reverted lockfile resolves `postcss` to **8.4.31**, but the current `package.json` still carries a `resolutions`/override entry pinning `postcss` to **8.5.10**. The two are now inconsistent.

- The pre-deploy checks did not catch it: `tsc --noEmit` and the PWA/GA4 test suites do not run `yarn install --frozen-lockfile`, so a lockfile/`package.json` drift is invisible to them.
- The current production build succeeded earlier because at that time its `package.json` resolution and its `yarn.lock` were mutually consistent. The revert reintroduced the mismatch against the newer `package.json`.

## Fix (belongs to E1 / source — one of the two, decide by intent)
1. **If postcss 8.5.10 is the intended version:** run `yarn install` (without `--frozen-lockfile`) at the repo root to regenerate `yarn.lock` so it reflects `resolutions.postcss = 8.5.10`, then commit the updated `yarn.lock` and redeploy.
2. **If postcss must stay at 8.4.31 (matching the reverted/prod lockfile):** remove or change the `postcss` entry in the `package.json` `resolutions` field back to `8.4.31` so it matches the committed `yarn.lock`, commit, and redeploy.

Either way, `package.json` and `yarn.lock` must agree on the `postcss` version before `yarn --frozen-lockfile` will pass. Do **not** work around this by dropping `--frozen-lockfile` in the build — that would silently change the dependency graph shipped to production.

## Notes
- No secret, env, DB, or domain change is involved or needed.
- Rollback target / current live build is already in place automatically: production still serves run `df981f72-8a5c-4a69-99ef-4c5faaa4b73c` (image `sha256:790216bcc67a7637987d6850aded1e076343943db48816aa31067610d88f4734`). No rollback action required; the failed run was never promoted.
