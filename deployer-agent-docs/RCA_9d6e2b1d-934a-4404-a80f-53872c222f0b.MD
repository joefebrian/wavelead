# RCA — M15 deploy failed at build_image (run 9d6e2b1d-934a-4404-a80f-53872c222f0b)

## Verdict
**Source-code fault. NOT a manifest/pipeline/infra fault.** The deploy is safe — the previous run (56cbcad4) is still live and serving; a failed build is never promoted.

## The misleading excerpt vs. the real cause
The trigger error surfaced the tail of **Step #0 "restore-pip-cache"**:
```
CommandException: No URLs matched: gs://emergent-default-customers-code/cache/grow-infrastructure/pip-cache.tar.gz
```
This is **benign** — a cold pip-cache miss (no cache object exists yet). The build proceeds past it. It is NOT what failed the build.

The **terminal failure is Step #2 "docker-build" → `yarn build`** (Next.js production build), full evidence from Cloud Build 04afe739 log lines 477–497:
```
⨯ useSearchParams() should be wrapped in a suspense boundary at page "/signup".
   https://nextjs.org/docs/messages/missing-suspense-with-csr-bailout
Error occurred prerendering page "/signup".
Export encountered an error on /signup/page: /signup, exiting the build.
⨯ Next.js build worker exited with code: 1
error Command failed with exit code 1.
ERROR: executor failed running [/bin/sh -c yarn build]: exit code: 1
```

## Root cause
Template is `nextjs_mongo_shadcn_base_image` (Next.js App Router). During `next build`, the `/signup` route is statically prerendered. A component on that route now calls **`useSearchParams()`** at render time **without a `<Suspense>` boundary**. In the App Router, `useSearchParams()` forces client-side bailout during static export; without a Suspense boundary around the component that reads it, the prerender throws and `next build` exits 1.

This is a direct side-effect of the **M15 "Safe auth return-to (?next=)"** change — reading the `?next=` query param on the signup/login page (lib/utils/returnTo.ts consumers). The prior live build (56cbcad4) did not read search params on `/signup`, which is why this is the first build to fail.

## Fix (source — E1 to apply in /app workspace; I cannot mutate source)
Pick ONE (option A is preferred — keeps the page statically optimizable):

**Option A — wrap the search-param reader in Suspense.** In `app/signup/page.tsx`, move the code that calls `useSearchParams()` into a child component and wrap it:
```tsx
import { Suspense } from "react";

function SignupInner() {
  const searchParams = useSearchParams();
  const next = searchParams.get("next");
  // ...existing signup UI that consumes `next`...
}

export default function SignupPage() {
  return (
    <Suspense fallback={null}>
      <SignupInner />
    </Suspense>
  );
}
```

**Option B — opt the route out of static prerender.** Add to `app/signup/page.tsx`:
```tsx
export const dynamic = "force-dynamic";
```

## Also check (same M15 change, same failure mode)
Any other route that now reads `?next=` via `useSearchParams()` — most likely the **login** page and any commercial-CTA return handler. Apply the same Suspense wrap / `force-dynamic` there, or the next build will fail on that page instead. A quick grep for `useSearchParams(` across `app/**` will surface every affected route.
